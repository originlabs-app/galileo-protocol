L1459@P31: 9.2.5 AuthenticateLRPFirst command
L1460@P31: The AuthenticateLRPFirst command reuses the same command code as
L1461@P31: AuthenticateEV2First. The distinction is made via the PCDCap2.1 parameter, as
L1462@P31: explained in Section 9.
L1463@P31: The AuthenticateLRPFirst command is fully compliant with the mutual three-pass
L1464@P31: authentication of ISO/IEC 9798-4 [7].
L1465@P31: The authentication consists of two parts: AuthenticateLRPFirst - Part1 and
L1466@P31: AuthenticateLRPFirst Part2. Detailed command definition can be found in Section 11.4.3.
L1467@P31: The protocol cannot be interrupted by other commands. On any command different from
L1468@P31: AuthenticateLRPFirst - Part2 received after the successful execution of the first part, the
L1469@P31: PICC aborts the ongoing authentication.
L1470@P31: During this authentication phase, the PICC accepts messages from the PCD that are
L1471@P31: longer than the lengths derived from this specification as long as LenCap is correct. This
L1472@P31: feature is to support the upgradability to following generations of NTAG 424 DNA TT.
L1473@P31: Apart from bit 1 of PCDCap2.1, which need to be set to 1 for AuthenticateLRPFirst
L1474@P31: resulting into 020000000000h, the content of PCDCap2 is not interpreted by the PICC.
L1475@P31: The PCD rejects answers from the PICC when they don’t have the proper length.
L1476@P31: Upon reception of AuthenticateLRPFirst, the PICC validates the targeted key. If the key
L1477@P31: does not exist, AuthenticateLRPFirst is rejected. At PICC level, the only available key is
L1478@P31: the OriginalityKey.
L1479@P31: The PICC generates a random 16-byte challenge RndB and send this in plain to the
L1480@P31: PCD. Additionally, the PICC and PCD reset both CmdCtr and EncCtr to zero and
L1481@P31: generate a random TI.
L1482@P31: Upon reception of the AuthenticateLRPFirst response from the PICC, the PCD also
L1483@P31: generates a random 16-byte challenge RndA. Now the PCD calculates the session keys
L1484@P31: SesAuthMACKey and SesAuthENCKey, as specified in Section 9.2.7. As explained there
L1485@P31: for LRP, a session key consists of a set of plain texts and an updated key.
L1486@P31: Then the PCDResponse computes a MAC over the concatenation of RndA with RndB,
L1487@P31: applying the SesAuthMACKey with the algorithm defined in Section 9.2.3. Note that
L1488@P31: MACs are not truncated during the authentication. Within AuthenticateLRPFirst - Part2,
L1489@P31: the concatenation of RndA and this MAC is sent to the PICC.
L1490@P31: Upon reception of AuthenticateLRPFirst - Part2, the PICC validates the received
L1491@P31: MAC. If not as expected, the command is rejected. Else it encrypts the generated TI
L1492@P31: concatenated with 12 bytes of capabilities to the PCD: 6 bytes of PICC capabilities
L1493@P31: PDCap2 and 6 bytes of PCD capabilities PCDCap2 that were received on the command
L1494@P31: (sent back for verification). Encryption is done according to Section 9.2.4, applying
L1495@P31: SesAuthENCKey.
L1496@P31: Note that part of PDCap is configurable with SetConfiguration. PCDCap2 is used to refer
L1497@P31: both to the value sent from the PCD to the PICC and to the value used in the encrypted
L1498@P31: response message from the PICC to the PCD where in this case the PCDCap2 is the
L1499@P31: adjusted version of the originally sent PCDCap2: i.e. truncated or padded with zero
L1500@P31: bytes to a length of 6 bytes if needed. After that encryption, the PICCResponse will also
L1501@P31-32: compute a MAC over the concatenation of RndB, RndA and the encrypted data.NXP Semiconductors NT4H2421Tx

L1507@P32: This section defines the LRP Non-First Authentication, which is recommended to be used

L1512@P32: This command is rejected if there is no active LRP authentication, except if the targeted
L1513@P32: key is the OriginalityKey.

L1523@P32: 9.2.7 Session key generation
L1524@P32: Next to the algorithms for MAC calculation and encryption, one of the major differences
L1525@P32: between the LRP secure messaging and the AES secure messaging is that the
L1526@P32: session keys are generated and already applied during the authentication with
L1527@P32: AuthenticateLRPFirst or AuthenticateLRPNonFirst.
L1528@P32: Also for the LRP protocol, two keys are generated:
L1529@P32: • SesAuthMACKey for MACing of messages
L1530@P32: • SesAuthENCKey for encryption and decryption of messages
L1531@P32: During the authentication, the SesAuthMACKey is used for both AuthenticateLRPFirst
L1532@P32: and AuthenticateLRPNonFirst. SesAuthENCKey is only used for AuthenticateLRPFirst.
L1533@P32: Being LRP keys, this section shows how both the plain texts and the updated key [10]
L1534@P32: related to these session keys are computed. In the remainder of the document, when
L1535@P32: the session key is applied in the LRP context the combination of those plain texts and
L1536@P32: updated key is meant.
L1537@P32: The session key generation is according to NIST SP 800-108 [8] in counter mode.
L1538@P32: The Pseudo Random Function PRF(key; message) applied during the key generation
L1539@P32: is the CMAC algorithm on top of the LRP primitive. This is specified in [10], see
L1540@P32: also Section 9.2.3. The key derivation key is the key Kx that was applied during
L1541@P32: authentication. Note that from this key a set of plaintexts and updated key is computed,
L1542@P32: so the static key is only used in this derivation. The generated session keys are AES
L1543@P32: keys. The input data is constructed using the following fields as defined by [8]. Note that
L1544@P32: NIST SP 800-108 allows defining a different order than proposed by the standard as long
L1545@P32: as it is unambiguously defined.

L1715@P34: 9.3 Secure Dynamic Messaging
L1716@P34: The Secure Dynamic Messaging (SDM) allows for confidential and integrity protected
L1717@P34: data exchange, without requiring a preceding authentication. NT4H2421Tx supports
L1718@P34: SDM for reading from one of the StandardData files on the PICC. Secure Dynamic
L1719@P34: Messaging allows adding security to the data read, while still being able to access it with
L1720@P34: standard NDEF readers. The typical use case is an NDEF holding a URI and some metadata, where SDM allows this meta-data to be communicated confidentiality and integrity
L1721@P34: protected toward a backend server.
L1722@P34: When using SDM, residual risks coming with the Secure Dynamic Messaging for
L1723@P34: Reading have to be taken into account. As SDM allows free reading of the secured
L1724@P34: message, i.e. without any up-front reader authentication, anybody can read out the
L1725@P34: message. This means that also a potential attacker is able to read out and store one ore
L1726@P34: multiple messages, and play them at a later point in time to the verifier.
L1727@P34: If this residual risk is not acceptable for the system’s use case, the legacy mutual
L1728@P34: authentication (using challenge response protocol) and subsequent secure messaging
L1729@P34: should be applied. This would require using an own application and operating outside a
L1730@P34: standard NDEF read operation.
L1731@P34: Other risk mitigation may be applied for SDM to limit the residual risk, without completely
L1732@P34: removing it:
L1733@P34: • Track SDMReadCtr per tag at the verifying side. Reject SDMReadCtr values that have
L1734@P34: been seen before or that are played out-of-order. This is a minimum requirement any
L1735@P34: verifier should implement.
L1736@P34: • Limit the time window of an attacker by requiring tags to be presented regularly (e.g. at
L1737@P34-35: least once a day) in combination with the previous mitigation.NXP Semiconductors NT4H2421Tx

L1745@P35: 9.3.1 SDM Read Counter
L1746@P35: In order to allow replay detection by the party validating the data read, a read counter is
L1747@P35: associated with the file for which Secure Dynamic Messaging is enabled.
L1748@P35: SDMReadCtr is a 24-bit unsigned integer. The SDMReadCtr is reset to 000000h when
L1749@P35: enabling SDM with ChangeFileSettings. In cryptographic calculations and represented
L1750@P35: with binary encoding on the external interface, the SDMReadCtr is represented LSB first.
L1751@P35: When represented with ASCII encoding on the contactless interface, it is represented
L1752@P35: MSB first. Note that this is in line with the NFC counter representation in [13]
L1753@P35: In not Authenticated state, the SDMReadCtr is incremented by 1 before calculating the
L1754@P35: response of the first read command, ReadData or ISOReadBinary, if successful. On
L1755@P35: subsequent read commands targeting the same file, the SDMReadCtr is not increased,
L1756@P35: and the current value is used. As soon as a different command has been received,
L1757@P35: the counter is incremented again on a subsequent read command. Also when varying
L1758@P35: between ReadData and ISOReadBinary, the counter is incremented on each first
L1759@P35: instance of the read command type. Note that the SDMReadCtr is not incremented when
L1760@P35: authenticated.
L1761@P35: If the SDMReadCtr reaches the SDMReadCtrLimit (see Section 9.3.2) or the value
L1762@P35: FFFFFFh (if SDMReadCtrLimit is not enabled) and a first read command arrives at
L1763@P35: the PICC, an error is being returned. Command chaining, see Section 8.5, does not
L1764@P35: additionally affect the counter increase. The chained command is considered as a single
L1765@P35: command.
L1766@P35: SDMReadCtr can be retrieved via the mirroring as part of the PICCData, see
L1767@P35: Section 9.3.3, or it can be retrieved via GetFileCounters.
L1768@P35: 9.3.2 SDM Read Counter Limit
L1769@P35: In order to allow limiting the number of reads that can be done with a single device
L1770@P35: applying Secure Dynamic Messaging, an optional SDM Read Counter Limit can be
L1771@P35: configured. There are two main use cases:
L1772@P35: • limit the number of usages from the card side. Note that typically this can also be
L1773@P35: controlled from the backend verifying the SDM for Read protected message.
L1774@P35: • limit the number of traces that can be collected on the symmetric crypto processing.
L1775@P35: This way potential side channel attacks can be mitigated, see also the Failed
L1776@P35: Authentication Counter feature for the mutual authentication. In this case, it is
L1777@P35: recommended to have the configured limit aligned with TotFailCtrLimit.
L1778@P35: The number of reads that can be executed for an SDM configured file can be limited by
L1779@P35: setting an SDM Read Counter Limit (SDMReadCtrLimit). This is an unsigned integer of 3
L1780@P35: bytes, related with SDMReadCtr. On the interface, the SDMReadCtrLimit is represented
L1781@P35: LSB first. The SDMReadCtrLimit can be enabled by setting a customized value with
L1782@P35: ChangeFileSettings. It can be retrieved with GetFileSettings.
L1783@P35: Once the SDMReadCtr equals the SDMReadCtrLimit, no reading of the file with
L1784@P35: ReadData or ISOReadBinary in not authenticated state can be executed. Note that
L1785@P35: if authenticated, reading is always possible even if SDMReadCtrLimit is reached,
